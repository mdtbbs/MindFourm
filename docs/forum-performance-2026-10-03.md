# 论坛性能与设计修复（2.5.2）

本次依据当前代码、独立回归与生产只读预检修复请求放大、无界回复树、权限投影、缓存并发和异步副作用问题。没有进行生产压力测试，不能据此给出并发容量或线上 P95 改善百分比。

| 问题 | 本次处理 |
| --- | --- |
| 回复逐条加载点赞、表情与附件 | 服务端批量读取，每批最多 100 个 ID；前端同一轮挂载合并请求，切换用户清理缓存并丢弃旧响应。隔离回归中 50 条回复的三类读取共 3 次请求。 |
| 一页根回复携带全部后代 | 根回复最多 50 条；返回 `child_count`，直接子回复独立分页，前端递归按需展开；保留翻页与孙级回复入口。 |
| 列表读取完整 Markdown/JSON/HTML | 帖子与首页卡片使用数据库截取摘要，作者与分类只读取公开字段；资源卡片省略完整文档、渲染图数据和存储路径，保留尺寸/build 标量及规范化标签供 Game Content 适配。 |
| 草稿、待审、群组帖子出现在发现入口 | 统一 SQL 可见性条件，在分页和计数之前过滤；公共缓存与 RSS 不含受限群组内容；批量接口和回复入口检查父帖子权限。 |
| 资源实体直接序列化 | 显式公开字段白名单；剔除用户邮箱等私有字段、文件路径与审核内部字段；保留版本兼容声明和授权非公开读取的驳回反馈；预览、下载和重渲染通过独立授权文件读取保留内部存储字段，公开 DTO 不承载文件操作。 |
| 热门资源对每条记录重复查三类事件 | 分别按最近 7 天分组聚合下载、点赞和收藏，再连接资源；补窗口索引；星球/尺寸过滤使用随 JSON 自动更新的虚拟索引列。 |
| 首页冷缓存并发重复构建、单分类拖慢整页 | 合并冷构建；首页与统一搜索分类设置 2.5 秒响应期限，各分类独立降级；保留 stale/unavailable 标记，搜索页提示部分结果缺失。 |
| 日期游标序列化与排序异常 | 日期统一毫秒编码、解码为 Date，排序加 ID；修正资源 updated_at 游标；搜索相关度先选择别名，避免 TypeORM JOIN 分页解析 CASE 表达式失败。 |
| 一个请求重复验证身份、频繁续期和活动写入 | 请求级 WeakMap 复用验证；Redis 原子读取/续期并节流，移动会话数据库活动更新采用时间与撤销条件。 |
| 保存成功后积分/通知失败导致接口报错 | 创建、发布、审核帖子/回复的事件与业务记录同一事务提交；worker 使用 Redis 分布式租约、退避重试；通知唯一键与用户行锁保护积分重试。提及通知检查收件人群组权限。 |
| 通知 SSE 只在一个进程可见 | 独立 Redis 订阅连接跨进程广播，保留本地立即交付并去除回环重复；Redis 故障时持久化通知仍可读取。 |
| 遥测最大值/P95/活跃用户定义错误 | 单次原子 Lua 聚合；跨小时最大值使用 MAX，慢请求分桶延伸至 30 秒以上并识别 V1 路由；活跃用户改为滚动 24 小时去重，并显示观察窗口是否完整。 |

## 验证

- 完整 Jest：182 个套件、1155 项测试通过，涵盖批量请求、可见性、用户切换、回复递归展开、事务失败及副作用重试。
- 后端构建、前端生产构建与 ESLint 通过；OpenAPI 检查通过（123 个路径、82 个 schema）。
- 真实隔离 Redis：并发原子计数/MAX、会话续期/撤销、去重活跃窗口、超过 30 秒的请求分桶、两个独立 SSE 订阅连接广播通过。
- 实际编译的 96 个实体通过 MySQL DataSource 元数据检查；真实 TypeORM 查询构造回归覆盖带 JOIN 的搜索分页。
- 新迁移在隔离 MariaDB 上执行、重复执行与回退通过。生产服务器为 MySQL 5.7.44，已核对官方 5.7 生成列表达式实现；生产 MySQL 5.7.44 已通过 MindOps 备份及迁移门禁；新生成列及索引存在，尺寸过滤 EXPLAIN 使用 idx_resources_filter_width。

## 仍需保留的边界

- 搜索保留 `%LIKE%` 子串语义；本次没有用全文索引替换结果语义。数据规模增长后仍需专项查询计划、容量测试或独立搜索索引。
- 2.5 秒分类期限保证聚合响应有界；Promise 超时本身不取消底层工作，主要卡片 SQL 另设置数据库执行期限。
- 新活跃用户指标需要观察满 24 小时；预热期不应与旧会话数量直接比较。
- outbox 依赖 Redis 租约执行，Redis 故障时待处理事件保存在数据库。最多自动重试 10 次，持续失败保留 `last_error` 与 `retry_count` 供运维处理。
- Redis Pub/Sub 不提供离线 SSE 重放；通知数据库仍是可靠读取来源。此次保持现有单进程部署配置，没有据此宣称整个论坛已完成集群化。
